01Issues at a glance

Eight problems that recur across the current chart set.

Most charts are technically correct but operationally wrong: they answer questions nobody asked, hide the answers to the ones people did, and re-spend precious page real-estate on near-duplicate views.

Redundancy

Four near-identical heatmaps

Coverage is shown four ways (avg/binary × appearance/guest). The binary-by-guest variant is within ±5pp of binary-by-appearance for every cell — one chart suffices.

Truncation

Bars don't sum to 100%

The gender chart drops "unknown" into a tiny grey label, so a 25% missing-data rate vanishes visually. Bars stop at 80%, suggesting completeness that doesn't exist.

Legibility

Overlapping data labels

"695 (25%)" sits on top of the 25% segment border; "Hochschullehrer" overlaps the axis caption; rotated show names collide with the median annotation.

No hierarchy

Categorical rainbow palettes

The treemap and occupation chart use 30+ unrelated hues. Color carries no meaning, so users decode position only — at which point a sorted bar chart would do the job better.

Cropping

Labels cut off the canvas

Radar axes read "Christlich D…", "So…", "on in Bayern" — the most important categorical labels in the chart are unreadable.

No ranking

Shows in arbitrary order

Every chart re-orders the 10 shows differently (alphabetical, by sample size, undefined). Eyes can't compare across panels because the axis keeps moving.

Wrong scale

Log axis where linear belongs

The "average values" heatmap uses a log color scale. A 0.01 cell and a 0.50 cell read as similarly pale; the StarTalk outlier of 12.79 dominates everything else.

No insight

Charts state, never argue

None of the 300 charts annotates a finding. The biggest story in the violin plot — StarTalk's median age is 22 years older than every other show — is left for the reader to spot unaided.

09System & code recommendations

The 300 charts come from one Python pipeline. Here's how to halve them.

Most issues we identified aren't per-chart — they're systemic. They stem from one config that maps every (property × cut × view) tuple into its own file. Below: a thinner spec, a shared theme, and four code-level rules that would propagate fixes across the whole set.

Current pipeline
Naive cartesian product
11 properties × 10 shows × 4 view variants ≈ 440 charts; per-property colormaps; per-figure ordering
# pseudo-code of what's running today
for prop in PROPERTIES:           # 11
  for cut in ["appearance", "guest"]:
    for norm in ["avg", "binary"]:
      for filt in SHOW_FILTERS:        # all/german/podcast…
        fig = px.bar(...)            # default order
        fig.update_layout(
          colorway = px.colors.qualitative.Plotly,
          title    = f"{prop} — {filt}",
        )
        fig.write_html(...)         # 4 near-duplicates
Symptoms. Four copies of every coverage chart. Inconsistent show order. Per-property palettes (sex/gender's blue vs occupation's orange clash). No shared "headline" annotation hook.
Proposed pipeline
Theme + spec + insight
one chart per (property, audience question); shared theme; canonical orderings
# 1. Single source of truth for show order & palette
SHOW_ORDER = canonical_show_order(by="sample_size")
THEME      = dict(
  colorway      = SEQ_BLUE,           # magnitude
  diverging     = DIV_REDBLUE,        # composition
  qualitative   = OK7,                # ≤7 named cats
  font_family   = "Inter, system-ui",
  paper_bgcolor = "#fafafa",
  margin        = dict(l=140,r=40,t=80,b=60),
)

# 2. Choose ONE cut per property based on r(appearance, guest)
def primary_cut(prop):
  return "guest" if corr(prop) > 0.9 else "both"

# 3. Every chart = data + question + headline annotation
def chart(prop, *, question, headline):
  df  = aggregate(prop, cut=primary_cut(prop))
  fig = render(df, kind=picker(prop), order=SHOW_ORDER, theme=THEME)
  fig.add_annotation(text=headline, xref="paper", …)
  fig.update_layout(title=f"{prop} — {question}")
  return fig

# 4. Sparse properties get a footnote, not a panel
if coverage(prop) < 0.05:
  emit_footnote(prop)               # no chart at all
Effect. 11 properties × 1 primary view ≈ 11 charts (down from 44 coverage variants). Show order, palette, font, margins, annotation are inherited — fixing the theme fixes every chart at once.

10Principles for the next 300 charts

Cut the set in half by following six rules.

01

One sort order, everywhere.

Pick a canonical show order — by sample size, by alphabet, or by the metric in question — and reuse it. Eyes shouldn't have to re-anchor between charts.

02

Make missingness visible.

"Unknown" is a value, not an annotation. Every percentage chart should sum to 100% with missing data shown as a hatched or muted segment.

03

Per-guest beats per-appearance.

Where the two correlate at r > 0.9 (which they do for all 11 properties), publish only per-guest. Footnote the per-appearance variant if you must.

04

Color carries meaning or it leaves.

Two-hue diverging for ordered data; sequential mono for magnitudes; categorical hues only when the categories are genuinely unordered and ≤7. The current rainbow treemap fails all three tests.

05

Annotate the headline.

Every chart should carry one sentence stating what it shows. If you can't write that sentence, the chart isn't telling you anything.

06

Linear unless proven otherwise.

Reach for log only when the data spans >2 orders of magnitude AND the smaller end matters. Most of the current heatmaps cover 0–10 — linear is correct.

07

Don't print what you can't read.

If a label rotates >45°, truncates at "…", or sits behind another mark, it isn't a label. Reserve 140 px of left margin for show names; let radar axes wrap or replace the chart.

08

Bucket the long tail.

Wikidata occupation has 800+ values; only 12 carry >1% mass. Bin the rest as "other (n=800)" rather than rendering 30 indistinguishable rectangles.

09

Composition ≠ volume.

Stop using one heatmap cell to encode both raw counts and proportions. Pair a sequential ramp (volume) with a position channel (proportion), as in the dot plot above.

10

Don't ship sparse charts.

If a property has <5% coverage (political ideology, viewer counts), the right output is a footnote, not a 1920×1080 PNG of mostly-white cells.
